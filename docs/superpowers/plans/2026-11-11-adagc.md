# AdaGC for LionPlus8Bit Implementation Plan

> **Status: approved and executed.** This document records the original design. Implementation results, the FP64 metadata deviation, raw commands, and remaining scientific questions are in `docs/validation-adagc.md`.
>
> **For agentic workers:** Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` only after implementation is requested. Steps use checkboxes for tracking.

**Goal:** Offer AdaGC as an explicit alternative to Lion+'s global gradient clipping while preserving the existing default behavior, mixed-precision safeguards, and native 8-bit momentum.

**Architecture:** Separate clipping preparation from the existing Lion update. Compute a coefficient and candidate history for each active parameter tensor, validate the complete step, then dispatch the existing native/master-weight/strict update paths. Keep compact clipping history outside bitsandbytes' lazy per-parameter momentum dictionaries.

**Tech stack:** Python >=3.10, PyTorch >=2.5,<3, pinned bitsandbytes 0.50.2; optional existing Triton numerical guard. No new runtime dependency in the first implementation.

**Spec:** The user's plan-only request; [AdaGC v4](https://arxiv.org/html/2502.11034v4), especially Section 4 and Algorithm 1; and the design decisions below. Baseline repository commit: `428830f1fcfe949f04c4f361a66ee34ee90f6f18`.

## Global constraints

- Plan only at this stage. Preserve all original snapshots, first-run evidence, and previous validation artifacts.
- Existing `clipping="global"` behavior and optimized execution flags remain the defaults. AdaGC is opt-in.
- Clip before both the Lion sign direction and its momentum update. Decoupled weight decay is not part of the clipped gradient.
- Keep one optimizer per device, dense supported gradients, contiguous parameters, original gradient object/value preservation, and the existing default-stream bridge.
- Do not add automatic distributed-shard, CUDA-graph, compilation, paging, or FP8 support claims. Keep their existing support limits.
- Report paper facts, proposed engineering extensions, measured results, and remaining uncertainties separately.

## Review focus

1. A tensor has zero gradients during warmup and becomes active later: its history must not permanently suppress learning. Covered in Task 1.
2. AMP overflows at the warmup boundary: weights, momentum, histories, and the counter must remain unchanged. Covered in Task 3.
3. A checkpoint restores FP16/BF16 parameters: clipping histories must retain their own precision and parameter mapping. Covered in Task 4.
4. A localized spike or tiny coordinate needs a different coefficient from another tensor: no global scalar or numerical-guard threshold may leak between tensors. Covered in Tasks 2 and 3.
5. Many small tensors are updated on a nondefault stream: avoid per-tensor host synchronization and preserve allocation lifetimes. Covered in Tasks 3 and 5.

## 1. Algorithm and explicit integration decisions

### Paper rule

For an entire parameter tensor `i`, let `n_i = ||g_i||_2` and let `gamma_i` be its previous history. After warmup:

\[
h_i=\min(1,\lambda_{rel}\gamma_i/n_i),\qquad
\widehat g_i=h_i g_i,\qquad
\gamma_i^{new}=\beta\gamma_i+(1-\beta)\|\widehat g_i\|_2.
\]

The threshold uses the **old** history. History observes the **clipped** norm; there is no EMA bias correction. During warmup, use global clipping and the running minimum of the resulting per-tensor norms. Paper settings are `beta=0.99`, `lambda_rel=1.04`, `T_start=100`, with global threshold `1.0` in its reported LLM configurations. This is historical-gradient clipping, distinct from AGC based on parameter norms. [AdaGC Section 4, Algorithm 1, Table 9](https://arxiv.org/html/2502.11034v4)

### Reference discrepancies

The [official project README](https://github.com/PaddlePaddle/PaddleFleet/tree/develop/Research/AdaGC) links both implementations below. Follow the paper's clipped-history rule and the author's PyTorch boundary rather than treating either implementation as an unquestioned oracle.

| Detail | Author's PyTorch patch | Linked Paddle implementation | Proposed package decision |
| --- | --- | --- | --- |
| Default warmup calls | 100; increment before comparison | 101 from its zero-based comparison | Exactly 100 completed optimizer steps |
| Warmup history | Minimum of globally clipped norms | Minimum of raw norms | Minimum of globally clipped norms |
| Denominator epsilon | `1e-6` | `1e-8` | Explicit zero branch; no additive epsilon |
| Gradient assumptions | FP32 CUDA gradients | Framework-specific integration | Preserve this package's FP32/FP16/BF16 contract |

Sources: [author's `megatron-llama.patch`, `clip_grads.py`](https://github.com/lishuai-97/AdaGC/blob/main/megatron-llama.patch), [Paddle implementation at linked PR revision](https://github.com/PaddlePaddle/Paddle/blob/1b1c6b5/python/paddle/distributed/fleet/meta_optimizers/dygraph_optimizer/hybrid_parallel_optimizer.py#L259). Both code paths use the target clipped norm for EMA updates even though epsilon slightly changes the actual norm. The package should derive history from the coefficient actually applied, with precision tolerances documented.

### Proposed API

Append keyword-only constructor options, preserving every existing positional argument:

```python
LionPlus8bit(
    model.parameters(),
    clipping="adagc",  # default remains "global"
    max_grad_norm=1.0,  # absolute warmup/bootstrap threshold
    adagc_beta=0.99,
    adagc_factor=1.04,
    adagc_warmup_steps=100,
)
```

- Retain the constructor's existing `max_grad_norm=4.0` default for compatibility. The example explicitly chooses the paper's `1.0`; do not change this silently when selecting AdaGC.
- After warmup, AdaGC replaces global clipping. There is no second global cap. `max_grad_norm` then applies only to cold-start bootstrap, not established histories.
- Use one policy and one set of AdaGC settings across the optimizer. Reject conflicting group overrides. Existing groups may still use their own Lion learning rates, betas, and weight decay.
- Validate `adagc_beta` in `[0,1)`, including rejection if its working-precision representation rounds to one; finite `adagc_factor >= 1`; and a nonnegative integer warmup excluding booleans. A factor of one cannot grow the clipping ceiling; recommend a value greater than one.
- Granularity is one original `nn.Parameter`, including biases, normalization weights, and embeddings; tied parameters are counted once. A flattened tensor changes the algorithm's granularity. Sharded logical tensors require a separate design.

### Edge-case policies: intentional engineering extensions

- Count completed `step()` calls containing at least one active gradient. The first 100 use global clipping; step 101 uses AdaGC. Calls with all `grad=None` and AMP-skipped calls do not count. An active all-zero gradient step still performs the ordinary Lion/weight-decay update and counts.
- `grad=None` leaves that tensor's history unchanged. New groups and tensors first activated after warmup begin unseeded.
- During warmup, update the minimum using **positive** clipped norms only. Zero observations do not initialize or reduce that minimum. A literal minimum including zero would otherwise trap every future positive gradient at zero.
- After warmup, an unseeded tensor's first positive gradient gets a per-tensor absolute bootstrap cap `min(1, max_grad_norm/n_i)` and seeds its history from that clipped norm. Other tensors continue AdaGC normally. This also defines zero-length warmup.
- For `n_i=0`, use coefficient one. An established post-warmup history follows the paper's EMA decay. If it decays below the smallest positive FP32 work value, mark it unseeded for a later positive observation; do not silently retain an unusable zero ceiling.
- Use an explicit safe denominator/zero branch rather than a fixed additive epsilon. This preserves scale behavior for very small gradients. Epsilon differences between reference implementations are not a proven best practice.
- Reject NaN/Inf gradients before any parameter, momentum, history, or step-counter update. Recompute suspicious reductions in FP64 to distinguish finite-gradient norm overflow from genuinely nonfinite input.
- Keep ordinary history and arithmetic FP32. Promote rare history entries and norm/ratio arithmetic to FP64 when FP32 would overflow or lose necessary tiny values. Never silently store an overflowed or flushed-to-zero history. Retain the existing refusal of positive clipping requests below FP32 gradient representability.
- Derive the normal-path clipped norm from the coefficient represented in the update path times the recovered input norm. In precision-sensitive fallback cases verify or measure the materialized clipped gradient's norm. Do not perform a second full norm pass on every ordinary gradient.

These policies must be identified as extensions in documentation and tested independently of literal paper equations.

### Relationship to Lion+

Leave Lion's momentum, sign update, weight decay, quantization, and master-weight policy intact. A sign update still depends on how the clipped gradient combines with momentum, so clipping is not redundant. Per-tensor adaptive thresholds change the original globally clipped Lion+ algorithm; its global-bound convergence claims cannot automatically be transferred. Quality and stability with quantized momentum remain empirical questions.

## 2. Mixed precision, memory, and execution design

### AMP and accumulation

Use the ordinary `GradScaler.step(optimizer)` integration. It unscales gradients before the optimizer runs and skips the optimizer call on overflow. Keep all AdaGC history/counter mutations inside `step()`; do not introduce backward hooks or a custom `_step_supports_amp_scaling` contract. Norms and history must observe the fully accumulated, unscaled gradient once per effective batch. [PyTorch AMP examples](https://docs.pytorch.org/docs/stable/notes/amp_examples.html)

Prefer FP32 parameters with autocast. With actual FP16/BF16 parameters, retain FP32 master weights and promote gradient work before scaling; clipping an FP16 temporary before promotion can underflow. FP32 masters still cost an additional `4 * number_of_parameter_elements` bytes independently of AdaGC. The author's FP32-only implementation and the paper's low-precision experiments do not establish this package's AMP correctness.

Important existing PyTorch restriction: ordinary `GradScaler` rejects unscaling FP16 `.grad` tensors (`torch/amp/grad_scaler.py`, `_unscale_grads_`). An internal FP32 master weight does not change the public parameter's gradient dtype. Therefore the supported GradScaler example and required real-AMP gate use FP32 parameters with FP16 autocast. Test actual FP16 parameters separately with finite, already unscaled gradients; do not advertise them as ordinary GradScaler-compatible. BF16 parameter training is a separate unscaled path. Adding a custom scaler/master-parameter integration is outside this first implementation.

### Packed histories and staged updates

Use an internal `_clipping.py` helper with:

- `ClippingConfig`: immutable policy/settings.
- `ClippingState`: packed device FP32 histories and initialization mask, exceptional FP64 entries, stable parameter-slot mapping, and completed-step count.
- `ClipPlan`: active-parameter coefficients, precision/strict-path flags, and candidate history changes for one step.
- `prepare_clipping(params, norms, config, state) -> ClipPlan`: no mutation of persistent history or gradients.
- `commit_clipping(state, plan) -> None`: apply candidate history and counter after successful dispatch.

Pack by stable parameter-group/order slots, independent of which gradients are active today. Rebuild or grow mappings on `add_param_group`; initialize new entries without modifying old entries. Keep ordinary history storage proportional to the number of tensors, with a few packed buffers rather than thousands of separately allocated CUDA scalars. Save the packed logical state once, avoiding serialization of scalar views into an entire buffer repeatedly.

Do not put clipping entries into a fresh `self.state[p]`: `_optimizer.py` currently uses an empty dictionary to decide whether to initialize bitsandbytes momentum. Keeping clipping state separate avoids accidentally skipping native initialization. Candidate histories are scratch state, not evidence that the step succeeded.

Validate the whole step before dispatch. Commit history after dispatch returns successfully. Do not promise rollback if a later native kernel fails after earlier tensors have already updated; document that limitation and require restart from a known checkpoint after a partial backend failure.

### Existing backend constraint and optimizations

Pinned bitsandbytes 0.50.2 accepts `gnorm_scale` as a **host float** and converts it to `ct.c_float`; it cannot consume a CUDA coefficient vector. See the local backend `_ops.py` and `backends/cuda/ops.py` under `verification_20261111/deps/bitsandbytes/`.

1. Reuse batched FP32 tensor-norm reductions. Prepare coefficients/history as packed vectors. Flag reductions needing FP64 recovery; rare recovery may require an additional rendezvous.
2. On the ordinary path, transfer coefficients and rejection/guard metadata together once, then pass the resulting host floats to the existing native calls. No `float(cuda_scalar)`/`.item()` inside the parameter loop. Target one normal-path host rendezvous for clipping preparation; profile it rather than claiming asynchronous execution.
3. Preserve native coefficient application for ordinary FP32 parameters. For master-weight and exceptional paths, materialize at most the current tensor's necessary gradient temporary. Avoid a model-wide foreach multiplication that duplicates every gradient.
4. Extend the numerical guard to use each tensor's coefficient-derived limit. Expose device guard flags for packing into the same host decision; preserve the current global wrapper. Initially allow a conservative optimizer-wide strict fallback if any tensor needs it; optimize that fallback only after correctness is established.
5. Preserve caller-to-default and default-to-caller stream waits for native bitsandbytes kernels. Record every new temporary/history storage on streams that use it; do not free staging storage while a native kernel is consuming it.
6. Reuse vector scratch storage after initialization. Measure actual allocated and reserved GPU memory: `4 bytes/tensor` describes history payload, not masks, FP64 exceptions, temporary vectors, allocator granularity, CPU mapping, or master weights.

A device-only coefficient path needs a changed bitsandbytes interface or different update kernels. Fused multi-tensor norm/guard preparation and native device-vector scaling are follow-up optimization experiments, not prerequisites or advertised capabilities. Compare them against the packed-host path before accepting their maintenance cost.

### Checkpoints

Increment `lionplus_config` to version 2 with clipping policy/settings and edge-policy identifier. Store canonical `lionplus_clipping` packed histories, initialization mask, FP64 exceptions, group lengths, parameter shapes, and completed-step count separately from bitsandbytes state. Explicitly restore clipping dtypes/device placement; bypass parent floating-state casting to FP16/BF16.

Validate configuration, mapping lengths/shapes, initialized-history finiteness/positivity, exception indices, and counters before applying the load. As with PyTorch optimizer state, callers must reconstruct the same group/parameter order; arbitrary reorderings among same-shaped unnamed parameters cannot be detected. Version 1 or legacy checkpoints lacking the new schema restore global clipping; they do not fabricate AdaGC history from momentum. Saved policy wins on resume and is visible in diagnostics. Policy switching on a populated optimizer is outside the first API: require a fresh optimizer and explicitly reset history rather than carrying statistics across modes silently.

## 4. Boundaries and unresolved empirical questions

- **Established by reading:** the intended paper rule; warmup/reference discrepancies; host-scalar bnb ABI; the current optimizer's global-scalar assumptions, lazy initialization trap, precision guard, and stream bridge.
- **Proposed, not verified:** API, packed state, zero-history recovery, precision promotion, batched readback, and checkpoint migration. Their acceptance gates are above; no AdaGC tests have run.
- **Requires experiments:** quality with quantized Lion momentum, sensitivity to cold-start recovery, behavior after LR/batch-size changes, actual small-tensor performance, peak memory, and long-horizon stability. Include a literal-paper reference on nondegenerate gradients and a zero-recovery ablation.
- **Distributed follow-up:** replicated DDP sees already synchronized full gradients; do not infer an extra global all-reduce saving there. FSDP/ZeRO/TP flattened or sharded tensors require logical-tensor norm reductions and shared history semantics before support. The paper's communication argument does not by itself implement that integration.
- **Potential later optimization:** fused preparation and a device-coefficient bnb interface. They must preserve quantization, strict tiny-value behavior, and stream ordering before adoption.
- **Theoretical limit:** removing the fixed global cap changes Lion+'s original assumptions. Adaptive clipping does not repair arbitrary numerical drift, upstream nonfinite values, or infrastructure errors.
